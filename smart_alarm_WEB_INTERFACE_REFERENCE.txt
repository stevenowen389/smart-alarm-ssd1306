SMART ALARM WEB INTERFACE AND SERVER REFERENCE
===============================================

Purpose
-------
Describes the behavior of the browser-based configuration interface
(smart_alarm/web/index.html, smart_alarm/web/java_functions.js) and the WSGI
server that backs it (smart_alarm/python_server.py). Companion document to
smart_alarm_SOURCE_INVENTORY.txt, which covers the whole repository at a
one-sentence-per-entry level; this file goes into more behavioral detail for
the web/server layer only.

Scope
-----
Covers: index.html controls, java_functions.js event handlers and their
server-bound requests, python_server.py request handling, and the
request/response contract with smart_alarm/data.xml. Does not cover the
alarm daemon (smart_alarm/smart_alarm) except where it reads the same
data.xml file and therefore affects web behavior.

===================
OVERALL DATA FLOW
===================

  Browser (index.html + java_functions.js)
      | GET  ./data.xml?cacheBust=<timestamp>   (loads current settings)
      | POST index.html  { field: value, ... }   (one field changed = one POST)
      v
  Apache + mod_wsgi -> python_server.py: application(environ, start_response)
      | writes field(s) into the in-memory XML tree, then serializes to disk
      v
  smart_alarm/data.xml  <-- also read/written independently by the alarm
                            daemon process (smart_alarm/smart_alarm) every
                            main-loop iteration.

Because the daemon and the web server are separate OS processes each holding
their own in-memory copy of the XML tree, python_server.py reloads the file
from disk (xml_data.read_data()) at the start of every POST request before
applying a change, so it never overwrites fields the daemon updated in the
meantime (e.g. test_alarm being reset to '0' after a test alarm completes).

======================
smart_alarm/web/index.html
======================
Static HTML shell; all interactivity is added by java_functions.js after
load. Key elements, by id/class:

time_date, time_hours, time_min, time_sec   Client-side clock display, driven entirely by the browser's own clock (not the Pi's).
cb_alarm_active                             Master on/off switch for the alarm.
btn_test_alarm                              Immediately triggers the alarm sound on the Pi (test_alarm=1).
hour_knob / minute_knob                     Rotating dials (jQuery Knob) that set the alarm_time.
cb_days_mon .. cb_days_sun (class cb_days)  Per-weekday checkboxes; values 1-6 = Mon-Sat, 0 = Sun, matching Python's time.strftime('%w').
sm_content                                  Selects alarm content: "mp3", "podcast", or "stream".
txt_content_podcast_url / txt_content_stream_url
                                             Free-text URLs for the podcast and stream content types.
sel_mp3_list (multiple select)              Lists MP3 filenames currently in smart_alarm/music/; supports multi-select for deletion.
btn_add_mp3_list (input type=file)          Native file picker; selecting a file immediately uploads it. 
btn_del_mp3_list                            Deletes every filename currently selected in sel_mp3_list.
cb_individual_message / txt_individual_message Toggles and text for a custom wake-up message; the alarm speaks a generated default message when disabled.
slider (#slider, jQuery UI)                 Volume control, 0-100.
class_hide                                  Marks the groups of controls that are always shown; the alarm no longer hides/shows this class based on cb_alarm_active.

=================================
smart_alarm/web/java_functions.js
=================================
Loaded once per page view; wraps all behavior in a single top-level jQuery
$(function(){...}) block. Uses two pieces of shared state: `initializing`
(true while the form is being populated from XML, to suppress POSTs caused by
programmatic .val()/.trigger('change') calls) and `mp3Array` (the current
MP3 filename list, used to map list selections back to filenames).

loadDoc()
    Issues a cache-busted GET (?cacheBust=Date.now(), Cache-Control: no-cache
    header) for ./data.xml so a browser refresh always shows the Pi's current
    on-disk settings rather than a cached response. Called on page load, and
    again after any successful upload/delete so the MP3 list and other
    fields reflect the latest state.

readXmlFile(xml)
    Parses the data.xml response and writes every value into its
    corresponding control: volume slider + text, hour/minute knobs and their
    text labels, alarm_active checkbox, content select menu and its
    associated URL fields, individual-message checkbox and text, the
    per-weekday checkboxes (checked state fully replaced, not just added to),
    and the MP3 select list (rebuilt from the <mp3_files><track> nodes).
    Sets `initializing = true` for the duration so that refreshing the
    widgets does not re-POST the values it just loaded.

Clock and date block
    Purely cosmetic: renders the day/date/month/year once from the browser's
    Date object, then updates hours/minutes/seconds every second via
    setInterval. Not synchronized with the Pi's clock or data.xml.

Checkbox handlers
    cb_alarm_active change   -> POST { alarm_active: 1|0 }
    .cb_days change          -> rebuilds the full comma-separated day list
                                 from every currently checked box and POSTs
                                 { days: "1,3,5" } (not incremental).
    cb_individual_message change -> shows/hides txt_individual_message and
                                 POSTs { individual_message: 1|0 }.
    All three skip the POST while `initializing` is true.

Knob handlers (jQuery Knob)
    change  callback only updates the on-screen hour/minute text as the knob
            is dragged.
    release callback fires once the user lets go: builds "HH:MM" from the
            current hour/minute text and POSTs { alarm_time: "HH:MM" },
            unless still `initializing`.

Volume slider (#slider)
    change  callback POSTs { volume: 50 + value/2 } -- note the value sent to
            the server is NOT the same 0-100 scale shown in the UI; it is
            remapped to 50-100 before being stored in data.xml.
    slide   callback only updates the visible volume_text while dragging.

Content select menu (.selectmenu)
    select  callback POSTs { content: "mp3"|"podcast"|"stream" }.
    change  callback toggles which of content_mp3_list / content_podcast_url
            / content_stream_url is visible; does not itself POST.

Text field handler (.class_input_text, focusout)
    On losing focus, POSTs one of { text }, { content_stream_url }, or
    { content_podcast_url } depending on which field id triggered the event.
    Skips the POST while `initializing` is true.

MP3 delete handler (#btn_del_mp3_list click)
    Reads every selected value from #sel_mp3_list (values are the filenames
    themselves, not array indices) and sends one
    POST { deleteMp3File: <filename> } per selected file in parallel via
    $.when/$.map. Calls loadDoc() only once all requests succeed; alerts the
    user if any deletion fails.

MP3 upload handler (#btn_add_mp3_list change)
    Rejects files over 25 MB client-side. Sends the picked File directly as
    multipart/form-data (FormData with a single 'uploadMp3File' field) via
    $.ajax({processData:false, contentType:false}) -- this avoids the size
    inflation and encoding overhead of Base64/urlencoded transfer used by
    earlier versions of this handler. Calls loadDoc() on success; alerts with
    the server's response body on failure.

Test alarm button (#btn_test_alarm click)
    POSTs { test_alarm: '1' } unconditionally; the alarm daemon detects this
    field, plays the alarm immediately, and resets it back to '0' in
    data.xml once handled.

==============================
smart_alarm/python_server.py
==============================
A single WSGI callable (`application`) is registered as the Apache
mod_wsgi entry point (see misc/apache/000-default.conf: WSGIScriptAlias /
... /python_server.py). A module-level `xml_data` (Xml_data instance) is
created once when the worker process starts and is reused across every
request handled by that process.

Request handling, in order:

1. If the request is a POST, parse the body with cgi.FieldStorage (handles
   both application/x-www-form-urlencoded field POSTs from $.post and the
   multipart/form-data upload from FormData).
2. Reload xml_data from disk (xml_data.read_data()) before applying any
   change, so this request cannot clobber fields the alarm daemon process
   changed on disk since the last request handled by this worker.
3. Iterate every posted field name:
   - 'uploadMp3File': the field is a file upload (has .filename/.file).
     The filename is sanitized with os.path.basename (prevents path
     traversal), the raw bytes are written directly to
     smart_alarm/music/<filename> in binary mode, and
     xml_data.readFileNamesInMusicDirectory() is called to refresh the
     <mp3_files> list in data.xml. Returns 400 with a short text body on
     failure instead of raising.
   - 'deleteMp3File': filename is sanitized the same way, the file is
     removed from smart_alarm/music/, and the MP3 list in data.xml is
     refreshed. Returns 400 on failure instead of raising.
   - anything else: treated as a direct data.xml field update via
     xml_data.changeValue(field, value); exceptions are logged, not raised,
     so one bad field does not break the response.
4. Regardless of method, serve a static file: PATH_INFO is mapped to
   ./web/<path> (or ./data.xml specifically for /data.xml), the file is
   read and returned with a MIME type from MIME_TABLE (falls back to
   application/octet-stream). Responses for data.xml include
   Cache-Control: no-store, no-cache, must-revalidate, max-age=0 so browsers
   always refetch the latest settings. Unknown paths return a 404 page via
   show_404_app.

content_type(path)
    Looks up the file extension in MIME_TABLE; unknown extensions fall back
    to application/octet-stream.

show_404_app(environ, start_response, path)
    Returns a minimal HTML 404 response linking back to the interface root.

__main__ block
    Only used for local/manual testing: runs the same `application` under
    wsgiref's simple_server on port 8090 and opens it in a browser. Not used
    by the Apache/mod_wsgi deployment on the Pi.

==========================
OPERATIONAL NOTES / GOTCHAS
==========================
- File permissions: Apache runs python_server.py as www-data. data.xml must
  be world-writable (chmod 666) and smart_alarm/music/ must be world-writable
  (chmod 777, not 775 -- www-data is not a member of the file owner's group,
  so group-only write access is not enough) for uploads, deletes, and XML
  field updates to succeed. bundle_send_and_update.ps1/.sh set both
  permissions automatically as step [6/6] of every deployment.
- Logging: python_server.py's logger writes to whatever handler mod_wsgi/
  Apache is configured with (typically Apache's error log), NOT to
  smart_alarm/logfiles/smala.log -- that file is only written by the
  separate alarm daemon process, which calls logging.config.dictConfig
  itself. Check Apache's error log to see python_server.py warnings.
- Stale in-memory XML: because xml_data is a per-process singleton reused
  across requests, any code path that writes the whole tree back to disk
  (changeValue, or the mp3-list refresh triggered by upload/delete) can
  clobber fields changed elsewhere unless the tree is refreshed first; see
  step 2 above.
- Weekday values: web checkboxes use 1=Mon .. 6=Sat, 0=Sun, matching Python's
  time.strftime('%w') used by the alarm daemon; a mismatch here would
  silently prevent the alarm from firing on the intended days.
